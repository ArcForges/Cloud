# Cloud repository instructions

Plan bounded changes before implementation. This repository owns the C# Native AOT Cloud service, its Docker image and its Cloudflare Container ingress Worker. The design authority for active development is the separate [ArcForges-Design](https://github.com/ArcForges/ArcForges-Design) repository ([AD-0001](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0001-flagship-pivot.md)).

- Work in an isolated worktree. Do not edit adjacent repositories as part of a Cloud change.
- C# decides every product and business step, including the AI Harness (P2-021). TypeScript here is a thin Cloudflare platform adapter only: the Worker entry and routing, the Container and Durable Object lifecycle, the run-alarm wake handle and the `ai.internal` outbound transport. An adapter makes no business decision, owns no authoritative state and holds no business constant except values generated from C# ([harness foundation](docs/harness-foundation.md)). The proof-only coordination and poison policy (`worker/foundation`) stays TypeScript in the proof bundle until CLOUD.05 moves it to C#, a named exception of the WorkerAdapter literal check (`tests/ArchitectureTests/WorkerAdapter`).
- Keep repository documentation in English. Preserve AGPL-3.0-only and third-party notices.
- Consume exact published Contracts packages: NuGet, and npm for `@arcforges/ai-internal` only. Never edit generated contracts here, copy sibling source, use submodules or add adjacent ProjectReferences.
- Keep the executable Native AOT compatible. Do not suppress trimming/AOT diagnostics to pass a build. Keep the final Linux image build; runtime execution is local opt-in.
- Commit the NuGet and npm locks; pin tools/base images/Actions. Dependency updates must pass locked restores and the relevant compilation and packaging checks.
- PR code must not receive deployment secrets. Main deployment promotes the sealed candidate image and Worker; never rebuild during publication.
- The production Worker and host serve one public method, the anonymous bounded stateless Hello. The ingress pipeline ([cloud-ingress](docs/cloud-ingress.md)) is the deny-by-default boundary every later method registers against by appending its policy and route; never add authenticated, commercial or AI behavior implicitly or serve a method that has no policy.
- Business persistence is named plans only: C# decides and asks the Worker to run one checked-in plan from `storage/plans/<owner>`; no SQL text, table name or ad hoc query is ever sent. A module project references only `ArcForges.Cloud.Modules.Abstractions` and touches only its own `<schema>_*` tables and the shared `platform_*` tables ([storage plans](docs/storage-plans.md)).
- One correlation identity per call is accepted or created at the edge, joined to one W3C `traceparent` from the Worker to the host and carried with a causation id in the job wake and the private job-slice call ([cloud-ingress](docs/cloud-ingress.md)). It uses only the wire fields `RequestMeta`, `ResponseMeta` and `ArcError` already define, adds no header or contract meaning, never takes part in authorization, and a malformed client value is refused with `validation.invalid_request`. Later hops (events, providers) reuse the seam; do not re-implement propagation per module.
- Readiness is reported per component (ingress, Container, D1, Durable Object, R2, Queue) from a closed vocabulary with no content, fails closed on a missing binding, a plan-manifest mismatch or a recovery-generation mismatch, and is served only on the operator-signed proof surface; production adds no route ([cloud-readiness](docs/cloud-readiness.md)).
- Keep the API route separate from Web's apex Custom Domain. Preserve binary gRPC-Web responses and status trailers.
- Run the checks in CONTRIBUTING.md. Distinguish unit, Docker, local Worker runtime, live Cloudflare and real browser evidence.
- Never read or print local credential stores, log tokens, commit secrets or request secret values in chat. Describe missing environment configuration explicitly.

## Flagship role

Cloud is an **active** repository of the ArcForges flagship ([AD-0001](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0001-flagship-pivot.md)). Per [architecture 01 §5](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/architecture/01-system-overview.md#5-repository-and-project-map), [architecture 10](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/architecture/10-cloud.md) and the [reuse classification](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/reuse/inventory-and-classification.md#3-cloud), it reuses the C# host, the Worker ingress, the guarded deploy scripts, the D1 storage layer (receipts, guard and commit tail) and the identity and entitlement domain rules and schema. On them it builds the flagship host profile, the new Fleet module and relay (`FleetHub` Durable Object), and new implementations of the identity, device, entitlement, commerce (Paddle and Google Play), notification, support, audit, configuration, operating-budget and operator endpoints. The flagship host profile composes only the modules it needs: Chat, Task, Agent, Sync, Resource, Search, Scope, PackageCatalog, Policy and Workspace are retained, not composed, and their tables stay untouched. Flagship surfaces deploy dark until production activation (Plan task AF-PROD-01).

## Delivery (serial, ArcForges/Plan)

Tasks for this repository come from the [Plan delivery graph](https://github.com/ArcForges/Plan/blob/main/delivery-graph.json) and are delivered under the Plan [execution policy](https://github.com/ArcForges/Plan/blob/main/execution-policy.md) and [delivery procedure](https://github.com/ArcForges/Plan/blob/main/delivery-procedure.md) ([AD-0014](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0014-delivery-method.md)). They are binding. The historical P2-018 model (delivery lanes, adoption slices, `delivery.py` claims and handoffs, parallel workers, integration-owner roles, leases, the build slot and the launcher) is retired and never resumed.

- One task is active at a time. Work only inside its write scope, in a worktree `.worktree/<task-id-lower>` on branch `task/<task-id-lower>`, never in the primary checkout.
- Delegated workers and reviewers work locally. Only the coordinator pushes, verifies the pushed head on both hosts, opens pull requests, merges (at the reviewed head, after the merge gate: the required statuses `arcforges/windows` and `arcforges/linux` for every PR, and hosted CI too for external PRs) and deploys through the guarded main-push path.
- Title pull requests `[<TASK-ID>] <summary>`.
- Shared files: each module (`src/ArcForges.Cloud.Modules.<Name>`) owns its own tables (`<schema>_*`), folders, plans (`storage/plans/<owner>`) and tests; cross-module changes use the declared participant interfaces of the guarded transaction families. D1 migrations are authored under their module prefix and take the next global sequence number; storage-plan manifest hashes are regenerated after rebase. Each module registers through its own entry point and route fragment while the host composition only lists modules. Each publication watermark, Durable Object alarm namespace and R2 prefix has one owning module and is reserved in the binding plan first.
- Implemented baseline: the anonymous Native AOT Hello host, its container image and ingress Worker with the WP02 build, dependency and provenance baselines; the nineteen module boundary projects, the Storage.D1 plan bridge and the `storage/plans` root (CLOUD.02); the physical D1 schema of every module, the typed exact adapters and the migration runner (CLOUD.03, [D1 physical schema](docs/d1-physical-schema.md)); the shared-family guarded-batch engine, the closed family registry and the family plan grammar (CLOUD.06, [shared families](docs/shared-families.md)); the commit tail, receipts, inbox, outbox publisher and change archive (CLOUD.04, [receipts and outbox](docs/d1-receipts-outbox.md)); the core identity model and its D1 store (CLOUD.11 and CLOUD.72, [identity core](docs/identity-core.md)), which resolve only in a composition that binds the plan executor (production binds none yet); and the HAR.40 C# executor foundation and Hello-agent slice ([harness foundation](docs/harness-foundation.md), [harness proofs](docs/harness-proofs.md)). The historical HAR.00 and AIR.00 tasks are not tasks of the current Plan.
- Earlier dated bootstrap and validation records under `docs/` describe their original scope; they are evidence, not execution instructions. Where older documents prefix a command with `delivery.py build-slot run … --` or assign a step to an integration owner, that is historical: run the wrapped command directly, and leave pushing and merging to the coordinator.

## Verification after the push (AD-0020)

Every PR into `main` is verified after the push, on the two verification hosts, and gated by GitHub ([AD-0016](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0016-local-first-verification.md) as amended by [AD-0020](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0020-post-push-verification-and-required-checks.md)). The flow: Push → Fetch → Local verification → Report status → Required checks → Review → Merge. The cross-repository rules are the Plan [AGENTS.md](https://github.com/ArcForges/Plan/blob/main/AGENTS.md) rules 6 and 7.

- **Push** the branch to GitHub; nothing is verified before a push. The only hook is the staged-whitespace `pre-commit` check. `python eng/verify.py install`, once per clone from the main checkout on `main`, installs it into the clone's common hooks directory and makes it executable. It also removes the retired pre-push hook and any `core.hooksPath`. Re-run it when `.githooks/` changes.
- **Two legs on two hosts** ([AD-0019](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0019-mcp-first-verification.md)). Each step runs on one host, `win` (native Windows) or `linux` (native Linux), and `eng/verify.py` runs only the leg of the host's own operating system, never through WSL or a remote shell.
  - The Windows leg runs on the Windows 11 workstation, through the Windows MCP server.
  - The Linux leg runs on the Linux MCP host, through the Linux MCP server.
  - Both are standard MCP servers that Claude Code and Codex share; their client configuration and credentials stay outside this repository. Local WSL is never a venue, not even as a fallback.
- **Fetch and verify on each host.** In the host's clone, fetch the pushed commit from GitHub and run the command in a worktree at it:

  ```
  git fetch origin <branch>
  git worktree add --detach .worktree/verify-<sha> <sha>
  cd .worktree/verify-<sha>
  python eng/verify.py run-and-report
  cd ../..
  git worktree remove --force .worktree/verify-<sha>
  ```

  For an external PR (Dependabot included), read the diff first; for one from a fork, fetch `refs/pull/<n>/head`.

- **Report status.** Each host reports the commit status `arcforges/windows` or `arcforges/linux` on that exact commit:
  - `pending` when it starts;
  - `success` only when every step of its leg ran and passed;
  - `failure` when a step failed, `error` when the leg could not complete.

  The command exits 0 after success, 1 when a step failed and 2 when the leg could not complete or be reported. The host reports with `ARCFORGES_STATUS_TOKEN` when set (a token limited to commit statuses), otherwise with its own `gh` login; steps never receive either through their environment, and neither is printed. The `gh` login stays readable from the host's `gh` configuration by the code being verified, so set `ARCFORGES_STATUS_TOKEN` on the host.

- **Required checks.** The `main` ruleset requires both statuses for every PR, with no bypass actors and the strict up-to-date policy; classic branch protection keeps requiring the hosted `Verify` check (skipped for the owner's PRs). The branch must be up to date with `main`, and every new push needs verifying again on both hosts.
- **Stop rule** (AD-0019 §5). If the Linux (or Windows) MCP server is unavailable, unreachable or its host lacks a prerequisite, stop and report the exact failure: the status stays missing and the PR cannot merge. Never skip, mock or weaken a step, or run the leg on another host (local WSL or an agent's own sandbox included).
- `python eng/verify.py list` shows the profile and each host's steps. `python eng/verify.py run` runs this host's leg of `HEAD` without reporting.
- **What runs.** The commit, never the working tree, as listed in `eng/verify_steps.py`: every validation job of `ci.yml` and the `candidate` that `deploy` ships, each on the host the hosted job used. Every change runs the full profile (the forbidden-term scan, Prettier and the provenance inventory read Markdown too).
  - Lane `win`, in `<main checkout>/.worktree/_verify`: `Source (windows-latest)`: `npm ci --ignore-scripts` (with the npm bundled with the selected Node), the locked restore and Release build of `Cloud.slnx`, `node tooling/project.ts licence-evaluated`.
  - Lane `linux`, in the Linux-native clone `~/.cache/arcforges-verify/Cloud`: `clone-identity` (the `origin` URL is this GitHub repository, which the forbidden-term scan requires, HEAD a local branch at the commit and `origin/main` the merge base, which `check:physical` and the provenance audit compare against; nothing is fetched from it), `fresh-intermediates` (removes the `obj/<configuration>/<tfm>` assemblies, which the architecture gate's project evaluation rewrites without their embedded resources, so every project compiles once, as in a fresh CI checkout), then `Source (ubuntu-latest)` and the dependency audit of `quality`: `npm ci --ignore-scripts`, `npm audit --audit-level=high`, `npm run check`, `npm run check:dotnet` (which also runs the EvaluatedRepositoryGate), `licence-evaluated`; then `candidate`: a clean-tree test and `npm run candidate` with `ARCFORGES_LOCAL_DOCKER_BUILD_NETWORK=host` (the image build's fetches use the host network, because Docker's default bridge network could not reach NuGet on the workstation's former Linux environment, and the host network works wherever the host reaches NuGet; the option is refused in CI, and the locked restore and digest-pinned base images keep the bytes the same) (the Linux Native AOT image in the Linux host's Docker, both Worker bundles as Wrangler `--dry-run` builds, the sealed tool, the verified manifest) at the local version `0.1.0-local.<milliseconds>`; its image tag is removed after a pass.
  - Lane `scan`: `git diff --check` and the pinned gitleaks image over the commits since the merge base with `.gitleaks.toml`, without network. `actionlint` when `.github/workflows/**` changed.
  - Not reproduced: the hosted architecture gate's RP-09 receipt (it trusts the secret scan only inside the GitHub `quality` job; locally RP-09 is the one accepted finding of the gate in `check:dotnet`, as in the hosted Linux source job), dependency review and CodeQL (GitHub services; external PRs, dispatch and the weekly schedule keep them). `CI` and `GITHUB_*` are not set and Cloudflare credentials are unset: nothing contacts Cloudflare.
- **Prerequisites** (installs are the user's): on Windows, the .NET SDK selected by `global.json`, Node as pinned in `.node-version` with its bundled npm, PowerShell 7 and Python 3.14; on the Linux host, the same .NET SDK, Node and npm as pinned (`.node-version`, `packageManager`), Python 3.14 (`python` on PATH), and a running Docker Engine with the pinned gitleaks image; on both, `gh` with a credential that can write commit statuses; network access to GitHub, the NuGet and npm registries and to `mcr.microsoft.com` for the pinned base images.
- **Failures.** A failed, timed-out or unrunnable step reports `failure` and prints the step, the last log lines and the log path (`<git common dir>/arcforges-verify/logs/`, with `summary.json`). Read the log, fix the cause, push, verify again.
- **Statuses and rulesets.** A status is reported only by `python eng/verify.py run-and-report` on the host it names, at the commit it verified. Never post, edit or copy an `arcforges/*` status by hand, and never change the ruleset, branch protection or required checks to get a PR merged.
- AI agents must never use `git push --no-verify` to bypass required validation.
- They must also never disable, remove, modify, or otherwise circumvent the hooks or required checks merely to get a change through.
- If validation fails, investigate and fix the underlying issue.
- If a required local test cannot run, do not silently skip it or claim successful verification.
- Changing `eng/verify*.py`, `.githooks/` or the ruleset as reviewed engineering work is allowed; changing them to get a change through is not.

## Efficient execution

The Plan's rule 7 applies. In this repository:

- Install once (`npm ci --ignore-scripts`, `dotnet restore Cloud.slnx --locked-mode`), then build incrementally: `dotnet build Cloud.slnx -c Release --no-restore`.
- While iterating, run only the affected checks: the changed test project (`dotnet test --project tests/ArcForges.Cloud.Tests -c Release --no-build`, with `--filter-class` for one class), the changed Worker test file (`node --test tests/worker/<name>.test.ts`), the changed generator or plan check (`npm run check:plans`, `npm run check:generated`, `npm run check:physical`), `npm run check:dependencies` after a bound input changed, `npm run typecheck`, `npx prettier --check <changed files>` and `dotnet format Cloud.slnx --no-restore --include <files>`.
- `npm run check`, `npm run check:dotnet` and `npm run candidate` are the full profile. It runs once per pushed head, on each host; `python eng/verify.py run` checks a leg before handover without reporting.

## Hosted CI

- **Owner PRs:** no hosted validation or security analysis; `Source`, `Dependency audit and repository checks`, `Dependency review`, `CodeQL`, the candidate and `Verify` show as skipped. `Verify` is the required hosted check (classic protection); a skipped `Verify` satisfies it. The `main` ruleset also requires the host statuses `arcforges/windows` and `arcforges/linux` for every PR ([Verification after the push](#verification-after-the-push-ad-0020)), which are the owner PRs' gate together with the review.
- **External PRs** (Dependabot included) and manual dispatches: the full CI as before: both `Source` legs, `quality` (audit, actionlint, the full-history secret scan, the build and the hosted architecture gate), dependency review (PRs), CodeQL for C#, JavaScript/TypeScript and Actions, the candidate after `source` and `quality`, and `Verify`, which requires every one of them. A dispatch with a proof input keeps its chain (`proof-access`, then `deploy-proof` after `Verify` and the candidate).
- **Main pushes:** delivery only: the candidate, then `deploy`, which needs the candidate and keeps its environment, concurrency, migration gate and steps. A broken candidate is caught before merge by the local profile, which builds it.
- **Schedule** (weekly): the security analysis: CodeQL and `quality` (dependency audit, the full-history secret scan, the build and the hosted architecture gate that must follow the scan in that job). No source or candidate job.

## Required validation limits

Follow [validation policy](docs/validation-policy.md), which supersedes older runtime and release-test requirements. Its Design authority is the historical [CI and local validation policy](https://github.com/ArcForges/ArcForges-Design-Parallel/blob/64173614f2c41543bfff8f6df8d5a9e41207eb0a/docs/assurance/ci-and-local-validation-policy.md) (ArcForges-Design-Parallel at `64173614`), except its rule 9 (parallel delivery), which AD-0014 supersedes; where they differ from the Plan execution policy, the Plan governs. Never add or execute macOS CI, device/emulator/GUI/browser E2E CI, live service or inference CI, installed-consumer CI or public-download verification. Keep runtime checks explicit local opt-in. Do not repeat public archive/hash checks, passing tests or post-merge runtime cycles. Preserve lock/signature/licence/provenance checks at actual trust handoffs. Do not configure proxy 7890 or install toolchains solely for testing. Stop and report the exact failed network operation. Linux opt-in checks run on the Linux MCP host, through the Linux MCP server, never through local WSL, not even as a fallback ([AD-0018](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0018-native-platforms-without-wsl-integration.md), [AD-0019](https://github.com/ArcForges/ArcForges-Design/blob/main/docs/decisions/AD-0019-mcp-first-verification.md)), on a Linux-native filesystem copy and never under a Windows mount such as `/mnt/c`, once per affected scope, recording the distribution, kernel, .NET SDK, clang, lld and Native AOT toolchain versions. Toolchains there are installed by the user; never SSH to a remote host. The host verification after the push ([Verification after the push](#verification-after-the-push-ad-0020)) is the one place the full build, tests and candidate run before a merge.

Dependency additions and upgrades follow [the enforced admission policy](docs/dependency-policy.md); update its input-bound review and retain the existing class and provenance gates.
