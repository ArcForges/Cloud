# Engineering controls of the Go center (AF-CTR-02)

AF-CTR-02 adds the Go center (`center/`, [center](center.md)) beside the C# code that stays until AF-CTR-09. This page maps every
existing engineering control of the repository to the risk it prevents, its Go equivalent (or why the C# control remains, and for
which code), the entry point that runs it, the stage where it runs and the evidence it leaves. The stages are:

- **hook**: the `pre-commit` hook (`.githooks/pre-commit`, installed by `python eng/verify.py install`);
- **native host**: the verification legs after the push, `win` on native Windows and `linux` on native Linux
  (`eng/verify_steps.py`, AD-0020), whose statuses `arcforges/windows` and `arcforges/linux` `main` requires;
- **hosted CI**: `.github/workflows/ci.yml` for external PRs (Dependabot included), manual dispatch and the weekly schedule;
- **release**: the `candidate` the Linux leg and the main push build, and the guarded `deploy` that promotes it unchanged.

`python eng/center.py check` is the single entry point of the Go controls on both legs and in hosted CI; on success it writes
`artifacts/center/checks.json` with the controls it ran and the executable's SHA-256.

Observed:

- **grpc-go**: `scripts/vet.sh` runs `go vet -all`, `gofmt -s -d -l`, `goimports`, `go mod tidy` with a clean-tree check,
  revive and `staticcheck -checks 'all'` with filtered exceptions; `vet-proto.sh` regenerates the protobuf code and diffs it;
  `testing.yml` runs the tests with `-race` and `-cpu 1,4` under timeouts; `govulncheck.yaml` runs daily and on changes;
  `deps.yml` compares the dependency set before and after a PR; CodeQL analyses Go.
- **caddy**: `ci.yml` sets `GOTOOLCHAIN: local`, builds with `CGO_ENABLED=0` and `-trimpath`, and tests with `-short -race`
  on Linux, macOS and Windows; `lint.yml` runs golangci-lint and govulncheck through actions pinned by SHA behind
  harden-runner; `.golangci.yml` enables an explicit list that includes errcheck, gosec, govet, staticcheck, unused,
  ineffassign, bodyclose, sqlclosecheck and misspell.
- **prometheus**: `Makefile.common` pins golangci-lint v2.14.0; `.golangci.yml` adds the gofumpt, goimports and gci formatters
  and linters such as depguard, errorlint, revive, staticcheck and unused; `Makefile.common` checks `go.mod` tidiness;
  `fuzzing.yml` runs native fuzz targets for its parsers (`go test -fuzz=… -fuzztime=4m`) and keeps failing inputs as
  artifacts; govulncheck and CodeQL run in their own workflows; zizmor lints the workflows.

## PostgreSQL driver, query and migration tooling (evaluation for part B)

Part A records the evaluation; part B implements the choice. The criteria are those of the task: type safety, compatibility with
the Neon pooler (PgBouncer in transaction mode, so no session state between statements), transaction control, cancellation,
licence and maintenance. Facts were checked on 2026-10-28 against the projects' repositories (latest releases: pgx v5.11.0,
2026-09-07; sqlc v1.31.1, 2026-04-22; bun v1.3.0, 2026-10-03; gorm v1.31.2, 2026-06-25; goose v3.29.0, 2026-10-11;
golang-migrate v4.20.1, 2026-09-09; Atlas v1.3.0, 2026-08-02).

**Driver and queries**

| Option                                       | Type safety                                                                                                  | Pooler compatibility                                                                                                                                                                        | Transactions and cancellation                                                                                               | Licence, maintenance                                                                  | Decision                                                                                                                                         |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| pgx v5 directly (`pgxpool`)                  | typed scans into Go values; SQL is hand-written and checked by the integration tests against real PostgreSQL | `QueryExecModeExec` sends each statement as an unnamed extended-protocol statement and keeps no prepared statement in the session; live evidence: the Hello on the Neon pooler (Cloud #110) | explicit `BeginTx` with isolation and access mode, `context` cancellation and deadlines on every call, `SET LOCAL` timeouts | MIT; already admitted and in production                                               | **chosen**                                                                                                                                       |
| sqlc over pgx                                | strongest: Go code generated from SQL and the schema                                                         | the generated code calls the pgx interface, so the exec mode applies                                                                                                                        | as pgx                                                                                                                      | MIT; adds a code generator and committed generated code to admit, pin and drift-check | not now: the store starts with a small set of platform statements; reconsider when a module's query count makes generation pay for its generator |
| `database/sql` with the pgx `stdlib` adapter | weaker (`any` scans, `sql.Null*`)                                                                            | as pgx                                                                                                                                                                                      | standard `database/sql` transactions; loses pgx's pool controls and PostgreSQL types                                        | BSD-3 / MIT                                                                           | rejected: adds an abstraction layer without a benefit for a PostgreSQL-only store                                                                |
