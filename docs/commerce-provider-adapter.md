# Commerce provider adapter

COM.01 implements the provider boundary in `ArcForges.Cloud.Modules.Commerce/Adapters`. The public port uses opaque references, canonical integer minor-unit money with explicit currencies, immutable purchase bindings, capability data, and normalized snapshots. Only internal adapter code knows Paddle endpoints, identifiers, headers, or payload fields. The production-source containment test also covers the restricted Worker adapter root admitted for CLOUD.74.

`BillingProviderFactory.Create` owns its HTTP handler and client. Production uses the fixed `https://api.paddle.com/` origin; sandbox uses its fixed sandbox counterpart. Infrastructure can inject a handler for CLOUD.74 restricted egress and certificate trust. This implementation does not enable Container internet access, change routes, install merchant credentials, or change data.

Operator configuration supplies credentials, one or two notification secrets for rotation, approved source identity, an approved HTTPS checkout page, and approved per-method capabilities. Settings deep-copy these capabilities. No commercial currency list, price, tax computation, merchant approval, or renewal cap is compiled into the adapter. Unsupported hosted checkout, portal, partial refund, cancellation, or reactivation is refused before mutation. Scheduled in-place plan switching and native mutation idempotency remain explicitly unavailable; COM.09 must use cancellation at period end followed by an admitted new purchase where its policy permits it.

Checkout reads the provider price and included product immediately before creating a transaction. Active product/price, tax category, region-specific unit price, currency, purchase kind, approved method/platform, and renewal cap must agree with captured server terms. A transaction contains the complete Realm, BillingAccount, Workspace, PurchaseIntent, CheckoutAttempt, Offer, PriceVersion, and PolicyVersion binding. The returned checkout URL must match the configured page and its transaction receipt. COM.03 still owns authenticated business authorization, approved active configuration, currency exponent conversion, durable attempt fencing, and checkout-page composition/merchant method restrictions; a provider read is never business authorization.

Transactions, subscriptions, adjustments, and paginated events have real authenticated reads for reconciliation. Pagination returns only validated opaque cursors; remote next URLs are never followed. Financial responses include allowlisted line-level unit and aggregate subtotal, discount, tax, total, and tax category with exact decimal text, and omit all payment instrument, address, and email fields. Credit, dispute, warning, and their reversals remain distinct. Current subscription periods are reconciliation evidence, not paid-service authority. Cancellation schedules the next billing period; reactivation clears only a scheduled cancellation. Full or item-level partial refunds call the actual adjustment API and preserve pending merchant approval. Portal sessions check customer/subscription ownership, validate the fixed portal host and temporary token, and suppress their URL from diagnostic stringification. Consumers must not persist or log temporary portal links.

The captured price includes its tax treatment (included, excluded, or merchant account setting). COM.03 must bind any account-setting choice to separately approved account configuration. A checkout receipt is not proof of the final charged amount: buyer address and tax can change on the hosted page. COM.04 must compare completed line financials with captured approved terms and required region evidence before fulfillment, quarantine discrepancies, and never manufacture tax or accept an unknown region as approved. The adapter rechecks returned transaction currency, price reference, quantity, base price snapshot, tax treatment, and internal metadata; an inconsistent accepted receipt is an unknown write outcome.

Every HTTP operation has bounded timeout, response bytes, JSON depth, and cancellation. Reads retry transport failures, HTTP 429, and server failures at most the configured count (maximum three), with bounded exponential backoff or bounded Retry-After. Mutations are never automatically retried. Network failure, timeout/cancellation after dispatch, server error, redirects, or an unusable accepted receipt produce `UnknownOutcome`. COM.03/COM.09 must fence that attempt and reconcile known remote state before any repeat. There is no invented idempotency header. Definitive client refusals have typed statuses and generic errors, without external body text or inner transport details. Disposal cancels in-flight work and owns handler disposal; independent requests can run concurrently.

Webhook verification uses the exact original bytes, timestamp-prefixed HMAC SHA-256, constant-time comparison, bounded signature fields, explicitly versioned operator keys for rotation, and default five-second freshness in both directions. Verification precedes JSON parsing. Duplicate JSON keys, partial internal metadata, malformed amounts/timestamps, and malformed supplier references are refused. The dedupe identity includes original event type and event ID. A receipt binds source, verification key version, algorithm, signed and verified times, original byte count/hash, and normalized projection hash. Supported verified events return deterministic UTF-8 version-one normalized projection bytes; every access returns a defensive copy. Unsupported or malformed events return no durable payload projection, only original digest/size and typed metadata; bounded invalid-signature inputs also expose digest/size without a verification receipt. An oversized input reports its size/refusal without hashing or processing the excess.

Raw provider bytes remain ephemeral and are never persisted by this adapter. COM.04 must protect the normalized projection and receipt together with its durable integrity mechanism, process/replay that exact projection, and never present it as a re-verification of the original signature. No payment instruments, credentials, or arbitrary provider metadata enter projections, quarantine, audit, or exports. Authenticated REST event/transaction reads supply independently fetched reconciliation evidence; they do not assert receipt of a signed webhook. COM.04 owns durable replay ordering, ledger/grants/outbox, and the reviewed provider-event storage amendment.

The component tests exercise the actual adapter with a fake unavailable HTTP transport: request authentication and binding, capabilities and regional prices, read reconciliation, refund approval, cross-customer refusal, cancellation/reactivation, signatures/replays/tampering/rotation, unknown and malformed events, retries and errors, cancellation before and after dispatch, timeout, concurrent calls, disposal, bounded bodies, redirects, malicious pagination, canonical money, and production containment. They do not prove real merchant delivery, Cloudflare deployment, or OS isolation.

Implementation delivery is separate from whole-series acceptance. CLOUD.74 owns restricted provider egress/trust composition; COM.03/04/09 own persistence, authorization, delivery and reconciliation composition. COM.14 and the WP50 acceptance owners must exercise the configured merchant sandbox/production behavior, payment-method approvals, tax/region mapping, real webhook delivery, refund/dispute handling, and recovery, plus verify the composed deployment before commercial acceptance. Event API retention is bounded by the provider, so it cannot establish complete history by itself.

Provider contracts were checked against the current official documentation on 2026-10-06: [transactions](https://developer.paddle.com/api-reference/transactions/create-transaction/), [price/product lookup](https://developer.paddle.com/api-reference/prices/get-price/), [transaction reconciliation](https://developer.paddle.com/api-reference/transactions/list-transactions/), [subscriptions](https://developer.paddle.com/api-reference/subscriptions/get-subscription/), [refund adjustments](https://developer.paddle.com/api-reference/adjustments/create-adjustment/), [events](https://developer.paddle.com/api-reference/events/list-events/), [temporary customer portal sessions](https://developer.paddle.com/api-reference/customer-portals/create-customer-portal-session/), and [webhook signature verification](https://developer.paddle.com/webhooks/about/signature-verification/).
